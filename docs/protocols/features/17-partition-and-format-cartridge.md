# Partition and format cartridge

## Overview and risk

Utility **Partition and Format Cartridge** recreates the cartridge partition/
filesystem. The supported choices documented for this Manager are NTFS and
exFAT. The operation destroys existing cartridge data.

It is also invoked as part of enabling/removing full-disk AES-256-XTS
encryption. The Manager dismounts the current volume, changes the layout,
formats it and waits for Windows to rediscover/mount it.

## Implementation overview

This is a host storage-management operation rather than a vendor SCSI format
command. The Windows build imports disk/volume management APIs and works with
RDXmon/Dokan for protected volumes. Normal OS block I/O reaches the device
through the storage stack while the Manager coordinates dismount, partition
creation, filesystem formatting and refresh.

Success means the new filesystem mounts and is writable/usable. Failures can
come from write protection, open handles preventing dismount, insufficient
privilege, device removal, Windows format failure or rediscovery timeout. The
executable recommends reboot/retry after certain encryption-removal format
failures.

The relevant Windows disk-layout and formatter entrypoints are identified
below; some helper wrappers remain unnamed in stripped code.

## Implementation details

The Windows implementation opens the physical disk/volume, reads the existing
layout with `IOCTL_DISK_GET_DRIVE_LAYOUT_EX`, constructs the requested new
layout, and applies it with `IOCTL_DISK_SET_DRIVE_LAYOUT_EX`. It then starts the
formatter path logged as `Start FormatEx2` for the chosen NTFS or exFAT
filesystem and waits for volume rediscovery. Encryption setup/removal invokes
this after the security/Dokan phase.

Open handles, write protection and missing privilege are checked by the OS;
the Manager reports the exact failed stage. Device refresh after layout change
is required because the previous volume object is no longer valid.

## Protocol details

This feature uses Windows storage-control IOCTLs and filesystem formatting,
not SCSI FORMAT UNIT:

```text
CreateFile(physical disk/volume)
 -> IOCTL_DISK_GET_DRIVE_LAYOUT_EX (0x00070050)
 -> prepare partition layout
 -> IOCTL_DISK_SET_DRIVE_LAYOUT_EX (0x0007C054)
 -> FormatEx2(NTFS or exFAT)
 -> close/rediscover/mount
```

Ordinary block writes generated by Windows carry the partition/filesystem data
to the cartridge. Their SCSI CDB sequence is OS-defined. A successful IOCTL
alone is insufficient; the formatted volume must reappear. Evidence anchors
are the `Start FormatEx2`, GET/SET DRIVE LAYOUT failure strings, VDS
`IVdsVolumeMF3::FormatEx2` call path near `0x0046A1E0`, and disk-layout logic
at `0x0046AA20`.

## PDF-derived defaults, confirmation and historical safeguard

New RDX cartridges are documented as NTFS-formatted. On Windows 7 or later,
the Format Selection dialog offers **NTFS (default)** or **exFAT quick
format**. After choosing, Manager displays an explicit deletion warning; only
confirmation starts the operation. Progress and the final result appear in the
bottom message area, and other utilities/tabs/close actions remain locked
until completion.

Windows release 0.1.0.30 added a software-encryption-related MBR check ensuring
that the disk signature is not zero. The reference layout routine confirms
that when it encounters zero it supplies a non-zero signature before applying
the MBR layout. This is a host partition-layout safeguard, not an RDX vendor
CDB.

Formatting is destructive regardless of whether it is run directly or as the
AES setup/removal continuation. Quick format recreates filesystem structures;
it must not be interpreted as cryptographic erasure for previously unencrypted
data.
