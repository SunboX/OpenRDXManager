# MCP integration specification — 2026-09-10

Historical design. This records the requirements and approach at the stated date; it does not establish current completion or hardware acceptance. See [verification](../verification/README.md) for recorded results.

Status: Approved and implemented. MCP acceptance passed; broader visual-test limitations are recorded in `docs/verification/mcp-verification.md`.

## Objective and coverage

Give an AI agent access to every supported OpenRDXManager operation and every public application, service, drive, cartridge, capability, and operation value. The GUI and MCP must operate on the same runtime and publish consistent state.

“All” means the functions and values the application actually supports. Preserve typed `reported` and `unavailable` fields, including their reasons, rather than inventing values or enabling operations that the native service marks unsupported. Passwords, encryption keys, internal session authority, and raw native command execution are not diagnostic values.

The current feature manifest explicitly marks several encryption, password, access-control, and automatic-authentication writes as evidence-incomplete. MCP will disclose this coverage and return the same capability failures. Implementing the missing native protocols is separate work.

## Approaches and recommendation

1. **Embedded Streamable HTTP server, with a small stdio bridge.** Recommended. The running Electron application owns the MCP endpoint, existing services, and single operation coordinator. Multiple clients share the state visible in the GUI. A stdio client launches only the bridge, which connects to that endpoint.
2. **Stdio as a dedicated application launch mode.** Suitable for a single local client but complicates attaching to an already-running GUI and keeping application logs off the protocol stream.
3. **Standalone MCP process connected directly to the native helper.** Useful for a future headless product, but would need to share or relocate settings, confirmation, firmware-file handling, logging, and operation ownership. It is unnecessary for integration into the existing desktop manager.

The proposed first implementation is local to this computer. Remote access requires a separate decision about deployment and authentication; binding the endpoint to all interfaces is not part of this design.

## Shared application boundary

Extract the schema-validated service dispatch from `src/main/ipc-controller.mjs` into a transport-independent main-process module. Keep Electron sender validation in the IPC adapter. MCP performs its own authentication before using the shared dispatch boundary; it must never fabricate a trusted Electron sender.

Reuse the existing `services` groups created by `src/main.mjs` and `src/main/service-runtime.mjs`, the existing schemas, and `OperationCoordinator`. Share device revision checks, capability decisions, native privileges, operation exclusion, confirmation bindings, firmware validation, cancellation boundaries, and terminal-log persistence.

Introduce a bounded public operation-state store fed by coordinator-accepted events. It exposes active and recent terminal operations by operation ID, including progress, results, cancellation state, and structured failures. Retain at most 128 operations for the application lifetime. Missing history returns `operation-not-found`; a restarted application never synthesizes completion from an absent record.

## MCP interface

Publish explicitly named, schema-described tools. Describe read-only and destructive behavior with MCP annotations, while enforcing permissions and safety in application code.

| Surface             | Agent access                                                                                                                                                |
| ------------------- | ----------------------------------------------------------------------------------------------------------------------------------------------------------- |
| Application         | Name, version, platform, public settings, service readiness, and feature coverage                                                                           |
| Discovery           | List devices, scan, refresh a selected device, and inspect discovery diagnostics                                                                            |
| Drive and cartridge | Full public snapshots, identities, firmware, capacity, usage, temperature, counters, status, modes, protection state, capabilities, and unavailable reasons |
| Diagnostics         | Start self-test, LED test, and write/read test; inspect progress and results                                                                                |
| Utilities           | Firmware update, supported drive-letter changes, formatting, drive mode, SATA mode, safe eject, and force eject                                             |
| Security            | Inspect existing protection/capability state and expose supported operations with their exact current availability                                          |
| Operations          | Inspect active/recent operations, request supported confirmation tokens, start operations, and cancel where allowed                                         |
| Settings            | Read and update every public setting through the existing persistence and GUI notification path                                                             |
| Support             | Read redacted activity, toggle logging, obtain/export summaries and activity, inspect help and compatibility information, and check updates                 |
| Service and desktop | Inspect/retry service setup, request existing registration/OS approval flows, show the application, select a device, and request normal guarded exit        |

Provide read-only resources for application state, devices, a device by ID, capabilities, operations, settings, activity, support summary, and help. Also provide read tools for clients that do not use resources. Keep resource URIs opaque to filesystem access.

State reads return the current validated snapshot with revision information. Hardware refresh is an explicit operation. Long operations return an operation ID promptly; clients can poll it or subscribe to updates supported by the negotiated MCP transport. Progress must come from accepted coordinator events, not raw helper events. Operation notifications become visible to both the GUI and MCP.

Expose a capability inventory covering every `OperationKind` and every feature-manifest entry. A test must fail when a new application feature lacks an MCP mapping or a documented external/platform limitation. UI layout and rendering are represented by their application actions and values; MCP does not automate arbitrary DOM clicks.

## Complete agent workflows

Some existing APIs assume GUI dialogs. Merely wrapping IPC would leave these workflows incomplete:

- **Firmware files:** factor the existing chooser's file-validation and token-creation steps into a shared main-only service. Add an MCP input for an explicit local firmware path. Preserve extension, size, regular-file, symlink, identity, lifetime, one-use token, native registration, and image validation checks. The renderer retains the existing chooser-only API.
- **Exports:** provide summaries and redacted activity directly as MCP content, plus export tools that write new files into an application-owned exports directory using generated filenames. Return the resulting local path without overwriting user files. Existing GUI save dialogs remain available to the GUI.
- **Confirmation:** formatting and force eject use the current exact-action, device-revision, service-generation, expiring one-use tokens. The confirmation tool describes the requested target and consequence. Obtaining such a token is an explicit client action, not proof of human approval; clients remain responsible for honoring the user's authorization. MCP must not silently request tokens on behalf of a start call.
- **OS approval:** service registration may require the operating system's approval UI. Tools report that state explicitly and let the agent inspect/retry it. The server cannot supply OS credentials or manufacture approval.
- **Exit:** return the accepted exit response before scheduling the existing guarded quit path. Closing an MCP connection never cancels an operation or stops the native runtime.

## Local endpoint and lifecycle

Use the official MCP SDK from native JavaScript ESM. Select and pin its released packages through npm during implementation; validate protocol compatibility using real SDK clients. The current official documentation identifies SDK v2 as the stable line.

The server is opt-in. Provide application settings for enabled state and a configurable local port; show endpoint status and provide a copyable client configuration. Bind explicitly to `127.0.0.1`, require a generated bearer token, validate Host and Origin, and bound request sizes and concurrent work. Apply authentication to every HTTP request, including subscriptions. Do not expose an unauthenticated discovery endpoint.

Store the token separately from public settings with owner-only permissions, and never publish it through general state resources, logs, errors, or support reports. The copied client configuration supplies the token-file path through an environment variable; clients may alternatively supply the token through secret environment storage. The stdio bridge reads its configuration without printing credentials or application logs to stdout.

Starting MCP must not change native service privileges or claim hardware availability. MCP bind failures appear in endpoint status without crashing the desktop application. Disabling MCP closes its listener and subscriptions while the shared coordinator continues active device work. Shutdown follows the existing operation policy and disposes MCP listeners and observers. Keep the Electron renderer sandbox defaults unchanged.

## Files and tests

Expected implementation areas:

- `src/main/application-dispatcher.mjs`: shared validated service routes.
- `src/main/mcp/`: SDK adapter, named tool/resource registry, local HTTP lifecycle, authentication/configuration, and public operation-state store.
- `scripts/mcp-stdio.mjs`: SDK-based bridge to the running application's authenticated endpoint.
- `src/main.mjs`, `src/main/ipc-controller.mjs`, and `src/main/service-runtime.mjs`: shared dispatch and lifecycle/event integration.
- `src/main/firmware-file-selection-service.mjs` and support services: complete dialog-independent agent workflows.
- Settings, narrow preload contracts, renderer controls, and all existing locale catalogs: MCP endpoint configuration/status.
- `package.json` and `package-lock.json`: installed SDK packages and test/bridge scripts.
- `docs/ai-agent-access.md`: setup, tool/resource catalog, authorization semantics, examples, errors, and capability limits.
- Focused `test/mcp-*.test.mjs` suites and existing IPC/runtime/firmware/settings tests.

Verification will cover real MCP initialization, discovery, tool calls and resource reads, authentication and input rejection, concurrent GUI/agent operations, stale revisions, token binding/expiry/replay, firmware file changes, cancellation, service loss, operation history, event delivery, and server disable/shutdown. Use deterministic injected services for hardware mutations and SDK client/server integration for protocol proof.

Run `npm test`, `env -u ELECTRON_RUN_AS_NODE npm run smoke`, `npm run format:check`, and `git diff --check`. Inspect the real Electron settings controls after visible changes. A local read-only MCP connection to the actual application provides runtime proof; it does not prove destructive device operations. Live hardware acceptance requires an explicitly selected device and authorization for the specific action.

Preserve all pre-existing checkout changes. This design does not authorize publication, packaging, signing, or release.
