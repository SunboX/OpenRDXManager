# Windows startup error observations

The installer workflow records an observation start immediately before the existing owned medium child test. After that test, a separate optional step reads existing local Windows error records through `scripts/observe-windows-startup-events.mjs` and `scripts/read-windows-startup-events.ps1`. The original native test, its deadlines and its fatal exit result are unchanged. The observation cannot authorize a Manager or turn a failed child test into successful startup.

The reader uses only the local Application and System event channels, restricted to IDs 1000, 1001 and 26 within the requested interval. The interval is at most five minutes. Each channel supplies at most 32 records, the reader has a five-second processing budget with 100-millisecond event reads, and its owning Node process imposes an eight-second process deadline and a 4 MiB output cap. Event XML rejects DTDs and external resolution; XML, field counts and field lengths have independent bounds. No event channel, WER setting, dump setting, account, token, security descriptor or device state is changed.

Raw captured fields remain inside the reader-to-Node process boundary. CI prints and archives only reconstructed categories for Application Error 1000, APPCRASH WER 1001, or Application Popup 26 records matching the fixed `openrdx-token-child.exe` name and interval. Arbitrary text, paths, identities, offsets, report IDs and native error strings are never forwarded. The JSON explicitly reports `correlation=fixture-name-and-time-only` and `startupProof=false`: it does not prove attribution to one exact child or identify a root cause. A reported Microsoft module may be where another problem surfaced, as described in [Microsoft's crash investigation guidance](https://learn.microsoft.com/en-us/troubleshoot/windows-server/performance/troubleshoot-application-service-crashing-behavior).

An empty complete query differs from a failed or bounded query. Neither proves that Windows recorded no error outside this short interval, nor that a failure did not happen. The observer does not wait for delayed error reporting or enable additional logging. The [EventLogReader API](https://learn.microsoft.com/en-us/dotnet/api/system.diagnostics.eventing.reader.eventlogreader.readevent) supplies the read timeout; the separate owning-process deadline covers reader startup and query failures too.

The closed output is retained only in `windows-token-diagnostics-*` as `windows-token-startup-events.log`, using the existing three-day retention. It is separate from installer/release assets. A malformed or unavailable observation cannot replace the original child-test result. On non-Windows hosts, the wrapper reports unavailable without executing PowerShell.

The focused Node tests exercise filtering, interval and size bounds, fixed reconstruction, privacy, provider schemas, unavailable readers, and preservation of the fatal workflow gate. On Windows, they also execute the authored XML parser through Windows PowerShell with synthetic valid, duplicate, oversized and entity-bearing XML. This parser test does not read event logs; an ordinary Windows VM check separately exercises the real local channel reader without touching the working Manager or dock.
