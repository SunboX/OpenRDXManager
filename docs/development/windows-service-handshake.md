# Windows service handshake

Read-only Windows discovery, filesystem and label queries retain zero-access volume handles after exact disk membership, topology and mount validation. They do not upgrade a newly inserted cartridge to raw read/write access merely to report it. Mutation leases still require the original read/write open; metadata-only leases reject lock, dismount, format, mount-point changes and file writes before any mutating API. Complete revalidation and ambiguity rejection remain required in both paths.

SCM `RUNNING` means that startup authority and the protected first pipe are established. It does not mean that per-client authentication and backend preparation have finished.

The native client first verifies its enrolled runtime, starts or queries the fixed service and proves the connected server's executable, process, account and SCM identity. The service independently verifies the client's session, process, executable, identification token and user, explicitly reverts identification impersonation, and rechecks its running authority. It retains the protected pipe namespace throughout this admission.

After acquiring hardware ownership and preparing the backend, the service arms the existing two-second first-frame reader, checks for STOP and writes the fixed 16-byte ASCII prelude `OpenRDX:ready:1\n`. The native client consumes exactly those bytes before publishing `connect` to the main process. Framed protocol version 1 then begins with the existing Manager handshake. The prelude is readiness evidence on an already authenticated pipe; it does not replace authentication.

Native activation and peer proof retain their original seven-second deadline. After successful proof within that deadline, all readiness-marker fragments share a separate 45-second absolute deadline. The service independently verifies the complete runtime before accepting and preparing a session; this work must not consume the peer-proof allowance. The client checks deadline and cancellation after synchronous and asynchronous completion. Missing, malformed, truncated, cancelled and late markers close the connection. There is no fallback to an older wire sequence. Client and service must be installed together. Extra bytes remain in the pipe for the existing frame decoder. The main process allows 98 seconds: 45 seconds for client runtime verification, seven for native activation, 45 for service readiness, and one second of watchdog margin. The client-verification allowance is an outer watchdog, not a separately enforced native verification deadline. The framed handshake retains its two-second bound and starts only after verified readiness. Installed Windows authentication smoke allows 120 seconds with a 135-second external process bound.

An early client may close before the listener accepts it, leaving `ConnectNamedPipe` reporting `ERROR_NO_DATA`. The listener disconnects that abandoned client on the same retained protected instance and continues under the original ten-second accept deadline. It does not drop namespace ownership or authenticate a merely listening instance. In nonblocking mode, a successful `ConnectNamedPipe` call can mean availability; only `ERROR_PIPE_CONNECTED` admits a connected peer to the existing authentication checks. These states follow [Microsoft's ConnectNamedPipe contract](https://learn.microsoft.com/en-us/windows/win32/api/namedpipeapi/nf-namedpipeapi-connectnamedpipe).

Native reads retain operation-owned handles, events, storage and their aggregate reservations until exact terminal completion is observed. Cancellation uses the original bounded drain; unresolved operations retain storage and budget until process teardown.

Complete runtime verification rereads and hashes every listed file. On Windows, a fresh fixed SHA-256 CNG state computes each file digest. Other platforms retain the portable SHA-256 implementation. There is no content cache or relaxed length, topology, enrollment or protection check.

The implementation is in `native/windows-client-addon/{service_ready.h,windows_pipe_io.h,openrdx_windows_client.cc}` and `native/rdx-service/src/bin/openrdx-hardware/windows_session.rs`. The portable parser fixture and Windows private-pipe fixture use no installed service or device. Installed authentication and read-only dock access remain separate acceptance gates.

For a hardware-equipped installed machine, run `npm run verify:packaged-app -- --installed --require-service --require-device --expected-device-id=rdx:...` with the exact previously identified dock's opaque ID. This runs the installed app's normal startup scan through its authenticated service and requires the selected identity in the authoritative inventory. An empty result fails even when the handshake and hardware capability flags pass. The test sends no mutating device operation. Omit `--require-device` on CI machines without connected hardware; authentication-only success is not discovery evidence.

Windows installer permission probing may skip unrelated disks whose identity cannot be proven. A Plug and Play `PROD_RDX` hint instead makes an open or identity failure fatal. The hint never authorizes a grant: the same complete, matching live standard/VPD identity remains mandatory before journaling and applying the fixed service SID's per-instance policy. Existing previous-policy restoration checks remain required. A driver/device reconnect can still be necessary to activate newly recorded instance security.
